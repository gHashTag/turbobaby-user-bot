# The TurboBaby `.t27` contract map

What each canonical contract owns, what it deliberately does not, and which contract it defers to.
Measured against the working tree on **2026-09-21**: **43 tracked specs, 33 658 lines** — 42 under
`specs/turbobaby/` plus the owner card `specs/agents/turbobaby.t27` — all 43 manifested in
[`scripts/verify_t27_specs.py`](../scripts/verify_t27_specs.py) and all 43 parsed, typechecked,
enumerated and code-generated by the pinned compiler (`gHashTag/t27@40003ed1`, the ref the
`t27-contracts` CI job checks out).

This file is the index. The history of the first merge stays in
[`t27-semantic-merge-matrix.md`](t27-semantic-merge-matrix.md); what the published corpus already
holds, and therefore what TurboBaby may write without duplicating it, stays in
[`t27-reuse-map.md`](t27-reuse-map.md).

## How a contract names another contract

The pinned compiler has no sound cross-file import: a brace import lowers to an empty `UseDecl`,
which `scripts/verify_t27_specs.py` rejects. So ownership is expressed as data, not as an import —
a string constant holding the other contract's `ID`, plus a test asserting the literal:

```
pub const REUSES_AVAILABILITY_ID : str = "turbobaby/availability";
```

A contract therefore never recomputes what a neighbour decided. It takes the decision as an abstract
parameter — `bookable: bool`, `units_available: i32`, `identity_present: bool` — and says whose
decision it is. Measured by sweeping every `pub const … : str = "turbobaby/…"` that is not the file's
own `ID`: **203 distinct contract-to-contract edges**, and every one of them resolves to a declared
`ID`. There is exactly one literal in the corpus that resolves to no contract, and it is deliberate:
`rental_terms.t27` keeps `TWIN_SPEC_ID = "turbobaby/rental_terms"` (underscore) as the legacy id of a
draft that was never tracked, guarded by `assert ID != TWIN_SPEC_ID`.

A second rule, learned the hard way: **a contract never cites a sibling by line number.** Four waves
of parallel authoring produced 72 such citations and most went stale within the hour — one moved
while it was being read. They are now three, each a quoted historical example that says so and is
pinned by an assertion. A live cross-reference names the owner's `ID` and the declaration.

Where a value genuinely has to appear twice (`ride_game.t27` holds seven arrays whose owner is
elsewhere, because a spec that cannot import cannot state its own laws without them), the copy is
marked: it carries the owner's ID and a drift invariant pinning length and elements against the
owner's declared values. A silent copy is the defect; a named one with a tripwire is not.

## The root

Only one contract names no other: **`market_profile.t27`** (`turbobaby/market`) — currency, minor
digits, timezone, and the declaration that no exchange rate exists in this repository. Everything
else in the corpus eventually reaches it.

Four more sit close to the root and are named far more often than they name: `availability`
(the bookability decision), `request_identity` (who a request is), `pricing_honesty` (where a price
comes from) and `ride_runtime` (the browser lifecycle). They acquired their own outbound edges once
the corpus grew around them, which is the graph working rather than a defect: `availability` reads
the market's currency, `ride_runtime` names the roster owner whose decisions it consumes.

## What each one owns, in one line

**Domain and price.** `availability` — the unit statuses and what counts as bookable.
`bike_catalog` — class, body, displacement, the family-versus-unit boundary and the publishable
fields. `rental_terms` — the term ladder in integer basis points, the class discounts, and the one
rounding rule. `deposit_tiers` — the per-family tiers, money XOR passport, and the refund identity.
`pricing_honesty` — where a price comes from, how an absent one renders, and D11's divergence
decision. `market_profile` — the deployment market as a declared profile.

**Transport and transaction.** `catalog_api` — the read boundary and its HTTP outcomes.
`catalog_write` — what an admin write may produce. `commerce` — cart to checkout to committed order,
the quote snapshot, idempotency, the dated line identity, and family capacity. `order_money` — the
arithmetic identity a submitted order must satisfy. `order_status` — the status vocabulary and which
values are terminal. `cart_persistence` — the gap between the cart the corpus declares and the cart
the database stores. `checkout_contact` — the contact details a checkout requires.
`delivery_terms` — the coverage rule, the window geometry and the one published area fee.
`http_cache` — what an ETag is computed over and the age a cached price carries.

**Identity, limits and the wire.** `request_identity` — the initData proof and the three gates.
`rate_limit` — the sliding window and its worst case. `api_surface` — the routed set against the
documented set. `client_errors` — what a customer is told when something fails.
`observability` — the correlation id and what a metric may claim. `webapp_bridge` — the client half
of every authenticated call and the DTO mirror. `upload_media` — the only gated write route.
`validation_bounds` — the shared validators, and where a clamp is forbidden.

**Money that is not a price.** `star_award` — the server side of a game payout and its ceiling.
`loyalty_ledger` — the bonus ledger's structure, without rates the repository does not publish.
`referral_program` — the code grammar, the self-edge guards, and the milestone ladder and
welcome credit it paid until the owner stopped them on 2026-09-26 (R3).
`referral_credit` — the inviter's 10% of each recorded completed rental of an invited friend, a
separate THB ledger, and the redeem or payout request a manager resolves by hand.
`game_score` — the high-score ledger and the discriminator it does not have.

**The game.** `ride_game` — the rideable roster and the handling model. `ride_runtime` — control
bounds, collision classification, once-only submission and teardown.

**Reach and content.** `bot_surface` — the command set and the callback grammar.
`deeplink` — the startapp payload and the compatibility roster. `notification_queue` — the outbound
queue and its dedupe. `promo_broadcast` — what may be promoted and what may be sent.
`ai_assist` — model output is entertainment, never an answer of record.
`events_booking` — capacity, the waitlist and the same-day rule. `happy_hour` — a discount window
and the clock it reads. `customer_surface` — which classes of claim the first screen may carry.
`locale_policy` — the published locales and the bare-key fallthrough.

**The tree itself.** `schema_provenance` — the migration sequence law, the established-database
probe, and the fail-open read. `runtime_config` — the rule about defaults, written because one
default pointed customers at another business. `legacy_retirement` — the three distinct states a
retired thing can be in. `publication` — what counts as proof that a spec is published.

## What the corpus refuses to state, and why

Each of these is a named refusal inside the contract that would otherwise own it — a constant plus a
note saying what is missing. They are the honest half of the migration, and none of them is a to-do
a spec may quietly fill in.

| refused | the owner that refuses it | what would be needed |
| --- | --- | --- |
| FX conversion of a deposit | `deposit_tiers`, `market_profile` | a published rate; `market_profile` declares the rate list empty and `DECISIONS.md` forbids deriving one |
| a persisted divergence record | `pricing_honesty` | a sink: no migration declares a divergence table, and both emission sites leave a log line |
| a door-latency or timeout bound | `pricing_honesty` | a distribution; exactly one sample exists in the seed |
| the composition order of class and term discount | `rental_terms` | an owner ruling; the seed publishes two tables and no order between them |
| a priced Phuket delivery table | `delivery_terms` | the owner's prices; the seed publishes one area fee and forbids interpolating the rest |
| loyalty tiers, cashback and usage caps | `loyalty_ledger` | a published source; the seed contains zero occurrences of loyalty and bonus |
| milestone amounts | `referral_program` | moot since 2026-09-26: the owner stopped the ladder (R3); the only referral money is `referral_credit`'s 10% |
| a reservation, hold or expiry for a rental | `commerce` | a mechanism; nothing in the tree reserves a unit |
| a count of confirmed overlapping rentals | `commerce` | a query; nothing counts them |
| `locked` and `abandoned` as stored cart states | `cart_persistence` | a column; the carts table has no status |
| a `game_key` discriminator | `game_score` | a migration; the word appears nowhere in the tree |
| the Queen board as a published surface | `publication` | an upstream change: the board answers, but with one repository string, and ignores `?world=` |

## The open decisions this migration surfaced

These are the owner's, not a contract's. Each is recorded where it belongs and none of them is
resolved by writing more `.t27`:

1. **The Koh Phangan delivery rows.** They are another shop's map, left in place deliberately
   (`085`), and TurboBaby's Phuket zones do not exist yet. *Decided 2026-09-24 by the owner:*
   `087` deactivates the four rows (deletes none) and ships the owner's eighteen Phuket zones with no
   ETA; `delivery_terms` records the table, and its out-of-belt price and the 17:30 cut-off as
   known and unmodelled.
2. **Which legacy surface retires next.** `legacy_retirement` measures three states; choosing what
   moves between them is a product call (issue #2).
3. **Whether `completed` stays an alias of `delivered`.** One column, five enumerations, four
   vocabularies.
4. **Whether the class discount composes with the term discount, and in which order.**
5. **Whether a cached catalog body may carry a price of any age at all**, given D11.
